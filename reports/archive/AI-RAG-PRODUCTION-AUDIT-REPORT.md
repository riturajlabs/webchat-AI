# AI RAG Production Audit Report

## 1. Root Causes Found

### Confirmed accuracy failures

1. Hybrid keyword search previously searched the full website candidate set and could introduce keyword-only chunks. This was fixed earlier by restricting keyword ranking to vector candidates.
2. Hybrid RRF scores were normalized relative to each result set. A weak vector hit could become `1.0` because it ranked first, defeating context filtering and confidence checks. RRF now controls ordering only; original vector scores are preserved.
3. Confidence abstention was disabled in production (`ENABLE_RAG_CONFIDENCE_CHECK=false`). Atlas always returns nearest neighbors, including for unrelated questions, so low-quality results could reach generation. Production configuration now enables the guard.
4. Context construction discarded every later chunk from the same document, even when those chunks contained distinct evidence. Exact duplicate text remains suppressed, but distinct chunks are retained.
5. Embedding batch validation checked only the first vector. Mixed-dimension provider output could pass ingestion validation. Every vector is now validated.
6. The deployment runbook documented a 3072-dimensional Atlas index while the active production configuration uses 1024 dimensions. The runbook now matches the current 1024-dimensional contract, and startup fails on observed stored-vector mismatch.

### Important remaining risks

- The configured embedding fallback order (`gemini`, `jina`, `cohere`) contains different embedding spaces. Equal dimensions do not make vectors interchangeable. A fallback query embedding compared with a corpus generated by another model can produce plausible but irrelevant neighbors. Production should use one embedding model per corpus, or store and enforce an embedding-space/version identity and reindex on changes.
- Retrieval cache entries are not invalidated immediately after crawl replacement or deletion; stale results can persist until TTL expiry.
- Cache size settings currently enable/disable namespaces but do not enforce an item-count bound in Redis. Redis `maxmemory` and an eviction policy should be enforced operationally or the cache abstraction should gain namespace capacity control.
- Adaptive rerank-top-k settings are configured but not applied per request.
- Atlas index creation remains a deployment responsibility. The `default` index must use the configured dimensions and cosine similarity.
- Confidence thresholds require calibration against a labeled retrieval set. The new metrics make calibration observable; the current threshold is a conservative guard, not a relevance proof.

## 3. Retrieval Flow Before and After

### Before

```text
Question
  -> sanitize
  -> query embedding
  -> Atlas vector top-k with tenant + website filter
  -> hybrid keyword reranking
  -> RRF score normalization
  -> optional reranker
  -> same-document suppression + min-score filter
  -> context
  -> LLM
```

### After

```text
Question
  -> normalize and validate
  -> query embedding
  -> Atlas vector top-k with tenant + website filter
  -> keyword reranking of vector candidates only
  -> RRF ordering, original vector scores preserved
  -> optional embedding reranker
  -> confidence decision and metrics
  -> exact-deduplicated, min-score-filtered context
  -> LLM only when confidence is sufficient
```

An unrelated query with weak nearest-neighbor scores now returns the fixed safe response:

> I could not find this information in the provided knowledge base.

## 4. Accuracy Improvements

- Prevented keyword-only website chunks from entering hybrid results.
- Prevented RRF normalization from hiding weak vector similarity.
- Enabled pre-generation abstention in production.
- Preserved distinct evidence chunks from the same source document.
- Added confidence metrics: confidence score, minimum score, average score, and rejected chunk count.
- Added explicit regression coverage for API-key retrieval, unrelated database-password queries, low confidence, tenant/website filtering, and mixed embedding dimensions.

## 5. Latency Improvements

Existing optimizations remain intact:

- Query embedding and retrieval caches avoid repeated provider/search work.
- Reranking reuses the query embedding and performs local cosine scoring over candidates.
- Hybrid keyword ranking no longer loads or scans the full website collection.
- Context has per-chunk and total character limits.
- SSE delta coalescing and provider timeouts remain enabled by existing configuration.

The confidence calculation and score restoration are local arithmetic and add negligible latency. Startup dimension validation is bounded to a small sample.

## 6. Remaining Risks

The highest production risk is embedding-space inconsistency during provider fallback. Before enabling cross-provider embedding fallback for an existing corpus, either keep one provider/model stable or add explicit embedding-space metadata and a reindex migration. Monitor the new raw vector DEBUG diagnostics temporarily, then use structured retrieval metrics and a labeled evaluation set for threshold calibration.

Cache invalidation, cache capacity enforcement, adaptive rerank behavior, Atlas index readiness probing, and a production retrieval benchmark remain follow-up work.

## 7. Production Readiness Assessment

**Status: improved, but conditional.** The retrieval pipeline now has materially safer score semantics, production abstention, stronger embedding validation, and correct context selection. Tenant and website filters are present in the Atlas query and existing isolation tests pass.

The system should not be considered fully enterprise-ready until the embedding fallback policy is made model-space safe, the Atlas index contract is verified in the production cluster, and confidence thresholds are calibrated against real relevant and unrelated questions. No production data, embeddings, crawler behavior, LLM provider, or prompts were modified.
